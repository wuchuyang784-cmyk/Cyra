## 2. 项目背景与业务目标

### 2.1 赛题背景

| 项目 | 内容 |
|------|------|
| 赛题名称 | A5：景区导览数字人 |
| 项目定位 | 面向景区导览、文化传播和互动体验的数字人系统 |
| 核心价值 | 用更自然的交互方式替代单向讲解，提升游客体验与文化传播效果 |
| 目标形态 | 以 Web/H5 为首期载体，支持数字人讲解、景点问答、路线推荐与角色切换 |

### 2.2 业务痛点

| 痛点 | 现状表现 | 对应目标 |
|------|----------|----------|
| 讲解形式单一 | 传统导游或录音讲解固定、互动性弱 | 提供可追问、可切换角色的数字人讲解 |
| 游览路线不够个性化 | 游客不知道先看什么、多久能逛完 | 根据时间、兴趣和景点状态推荐路线 |
| 文化内容传播浅 | 用户只能看到简介，难以理解人物、典故和文化背景 | 通过角色化表达增强内容吸收和记忆 |
| 景区内容维护成本高 | 新景点、新故事上线依赖开发改代码 | 建立内容配置与发布机制，降低维护门槛 |

### 2.3 项目目标

| 编号 | 目标 | 说明 |
|------|------|------|
| G1 | 提升互动讲解体验 | 用户可围绕景点内容进行追问，而不是只听固定播报 |
| G2 | 提供实用导览能力 | 系统能根据用户约束条件给出可执行的游览路线 |
| G3 | 形成差异化文化表达 | 支持至少 2 到 3 个角色形象，体现不同讲解风格 |
| G4 | 兼顾内容运营 | 非开发人员可以维护景点、人物和问答素材 |

### 2.4 首期默认假设

| 假设项 | 默认值 |
|--------|--------|
| 景区范围 | 首期只覆盖 1 个景区 |
| 景点规模 | 首期配置 10 到 20 个景点的结构化内容 |
| 角色数量 | 首期提供 2 到 3 个数字人角色 |
| 交互方式 | 首期以文本问答为主，语音交互作为增强能力接入 |
| 交付终端 | 首期交付 Web/H5 端，AR 和复杂感知能力不纳入必做范围 |

## 3. 干系人与用户角色

### 3.1 干系人

| 角色 | 关注点 |
|------|--------|
| 游客 | 路线是否好用，讲解是否有趣，问答是否准确 |
| 研学学生 | 内容是否易懂、有趣，是否具备互动和游戏感 |
| 景区运营人员 | 景点内容是否易维护，角色和活动素材能否快速上线 |
| 内容审核人员 | 历史文化内容是否准确，是否有来源和审核记录 |
| 项目团队 | 首期范围是否可控，模块边界是否清晰，是否便于比赛展示 |

### 3.2 用户画像

| 用户类型 | 主要特征 | 典型需求 | 主要痛点 |
|----------|----------|----------|----------|
| 家庭游客 | 时间有限，希望高效游览 | 想快速了解必看景点和推荐路线 | 不熟悉景区，不知道怎么规划 |
| 研学学生 | 好奇心强，愿意互动 | 想通过问答和故事理解文化背景 | 传统讲解偏枯燥，缺少参与感 |
| 历史文化爱好者 | 愿意深挖内容 | 想获得更深入的典故和人物关联 | 普通导览内容太浅 |
| 景区运营人员 | 关注活动、内容更新和展示效果 | 想低成本更新景点、角色和导览文案 | 依赖开发改内容，响应慢 |

## 4. 范围定义

### 4.1 首期范围（MVP）

| 类别 | 首期范围 |
|------|----------|
| 前台浏览 | 景区主页、景点列表、景点详情浏览 |
| 导览能力 | 基于用户时间和兴趣的推荐路线生成 |
| 讲解能力 | 面向景点内容的数字人讲解 |
| 问答能力 | 面向景区文化与景点内容的智能问答 |
| 角色能力 | 2 到 3 个数字人角色的切换与风格化表达 |
| 运营能力 | 基础内容维护能力，包括景点、角色和问答素材更新 |
| 数据闭环 | 关键交互日志记录，便于问题回溯与答辩展示 |

### 4.2 后续迭代范围

| 类别 | 后续迭代范围 |
|------|--------------|
| 语音增强 | 语音识别与语音播报 |
| 多语言能力 | 多语言和方言支持 |
| 场景智能 | 用户情感识别与场景感知 |
| 沉浸式展示 | AR 实景标注 |
| 终端扩展 | 小程序、AR 设备和更多终端适配 |

### 4.3 本期不做

| 不纳入项 | 原因 |
|----------|------|
| 高精度室内外实时定位 | 实现复杂度高，不属于首期最小闭环 |
| 完整 3D 数字人实时渲染引擎自研 | 与比赛周期不匹配，可采用轻量展示方案 |
| 全景区实时人流预测与复杂调度 | 对数据和基础设施依赖过强 |
| 完全开放域问答 | 容易失控，无法保证文化内容准确性 |
| 无审核直接发布文化内容 | 不符合内容治理要求 |

## 5. 核心业务场景

| 编号 | 场景 | 参与角色 | 触发条件 | 主流程 | 结果 |
|------|------|----------|----------|--------|------|
| UC-01 | 景点讲解 | 游客、学生 | 用户进入景点详情或点击“开始讲解” | 系统展示景点信息，调用数字人按当前角色输出讲解内容 | 用户获得基础介绍和进一步提问入口 |
| UC-02 | 路线规划 | 游客 | 用户输入停留时长、兴趣偏好、起点或目标景点 | 系统筛选景点、生成推荐路线并说明推荐理由 | 用户得到可执行的游览顺序和预计耗时 |
| UC-03 | 文化问答 | 游客、学生、文化爱好者 | 用户围绕景点、人物、典故发起提问 | 系统识别问题类型，检索知识内容，按角色风格生成回答 | 用户获得针对当前景区上下文的回答 |
| UC-04 | 角色切换 | 游客 | 用户主动切换数字人角色 | 系统加载新角色配置，保持当前景点上下文不丢失 | 讲解风格改变，但事实内容保持一致 |
| UC-05 | 内容维护 | 景区运营人员、审核人员 | 后台新增或更新景点、角色或问答条目 | 系统保存草稿，审核通过后发布 | 前台可展示最新内容，变更可追溯 |

## 6. 功能需求

### 6.1 P0 核心需求

#### FR-01 景区与景点信息浏览

| 项目 | 内容 |
|------|------|
| 编号 | FR-01 |
| 优先级 | P0 |
| 主要角色 | 游客、学生 |
| 说明 | 用户可以查看景区概览、景点列表和景点详情，作为导览、讲解和问答的入口。 |
| 输入 | 景点选择、景点筛选条件、当前所在页面 |
| 输出 | 景点名称、简介、图片、标签、建议停留时长、讲解入口 |
| 验收标准 | 1. 用户可在 3 步内进入任一景点详情。<br>2. 每个景点至少包含名称、简介、标签和讲解入口。<br>3. 景点内容缺失时，系统给出兜底提示而不是空白页面。 |

#### FR-02 路线推荐与导览

| 项目 | 内容 |
|------|------|
| 编号 | FR-02 |
| 优先级 | P0 |
| 主要角色 | 游客 |
| 说明 | 系统根据用户时间、兴趣和必看景点偏好，生成推荐游览路线。 |
| 输入 | 可游览时长、兴趣主题、起点、必看景点、避开项 |
| 输出 | 推荐路线、景点顺序、预计总耗时、每个景点的停留建议、推荐理由 |
| 验收标准 | 1. 用户至少可以按“时间”和“兴趣”两个维度生成路线。<br>2. 系统返回的路线包含顺序、预计耗时和推荐理由。<br>3. 当约束过多导致无法生成路线时，系统返回可理解的调整建议。 |

#### FR-03 数字人景点讲解

| 项目 | 内容 |
|------|------|
| 编号 | FR-03 |
| 优先级 | P0 |
| 主要角色 | 游客、学生 |
| 说明 | 数字人围绕当前景点输出结构化讲解内容，支持角色化表达。 |
| 输入 | 当前景点、当前角色、讲解触发动作 |
| 输出 | 讲解文本，可选语音播报，以及与当前角色匹配的表达风格 |
| 验收标准 | 1. 每个 P0 景点都能触发讲解。<br>2. 切换角色后讲解风格发生变化，但核心事实不变。<br>3. 讲解内容应标记内容来源或来源类型，便于审核。 |

#### FR-04 景区文化智能问答

| 项目 | 内容 |
|------|------|
| 编号 | FR-04 |
| 优先级 | P0 |
| 主要角色 | 游客、学生、历史文化爱好者 |
| 说明 | 用户可以围绕当前景点、景区人物和相关典故发起自然语言提问。 |
| 输入 | 用户问题、当前景点上下文、当前角色 |
| 输出 | 问答结果、是否命中知识库、必要时的兜底提示 |
| 验收标准 | 1. 系统优先回答与当前景区和景点相关的问题。<br>2. 对超出知识范围的问题，系统明确说明“暂不确定”并给出引导，而不是编造答案。<br>3. 对敏感、违规或无关问题，系统有明确拦截策略。 |

#### FR-05 角色切换与人物风格管理

| 项目 | 内容 |
|------|------|
| 编号 | FR-05 |
| 优先级 | P0 |
| 主要角色 | 游客、景区运营人员 |
| 说明 | 系统支持在同一景区场景中切换多个数字人角色，并维护角色的人设一致性。 |
| 输入 | 角色选择、角色配置、当前会话上下文 |
| 输出 | 新角色的讲解风格、展示信息和可用能力边界 |
| 验收标准 | 1. 首期至少支持 2 到 3 个角色。<br>2. 角色切换后不丢失当前景点上下文。<br>3. 角色配置应包含身份、语气、典型表达、知识范围和禁答边界。 |

### 6.2 P1 支撑需求

#### FR-06 内容维护与发布

| 项目 | 内容 |
|------|------|
| 编号 | FR-06 |
| 优先级 | P1 |
| 主要角色 | 景区运营人员、审核人员 |
| 说明 | 运营人员可以维护景点、路线、角色和问答素材，并通过审核后发布。 |

#### FR-07 交互日志与问题回流

| 项目 | 内容 |
|------|------|
| 编号 | FR-07 |

#### FR-08 多终端适配与语音增强

| 项目 | 内容 |
|------|------|
| 编号 | FR-08 |
| 优先级 | P1 |

## 7. 数据与内容需求

| 数据对象 | 关键字段 | 用途 | 质量要求 |
|----------|----------|------|----------|
| 景区信息 | 名称、简介、开放时间、主题标签 | 作为首页和导览入口 | 信息完整、来源明确 |
| 景点信息 | 名称、位置、简介、停留时长、关联故事 | 讲解与路线推荐的基础 | 每个景点至少有 1 条讲解内容 |
| 路线模板 | 主题、景点序列、时长、适用人群 | 路线推荐和兜底方案 | 可人工维护和调整 |
| 数字人角色配置 | 身份、语气、典型表达、知识边界、禁答规则 | 支撑角色切换与风格化输出 | 必须经过内容审核 |
| 文化知识条目 | 标题、正文、标签、来源、适用景点 | 支撑问答和讲解扩展 | 必须记录来源和更新时间 |
| 交互日志 | 会话编号、时间、问题、命中状态、错误码 | 支撑问题回流和性能分析 | 需脱敏存储 |
| 审核记录 | 内容编号、审核人、状态、意见 | 支撑内容发布治理 | 可追溯、不可缺失 |

| 内容治理项 | 要求 |
|------------|------|
| 来源管理 | 所有对外展示的文化内容都应具备来源说明 |
| 审核机制 | 涉及历史人物、典故和景区介绍的内容需要经过人工审核 |
| 角色分层 | 数字人角色配置要区分“事实知识”和“表达风格”，避免角色化表达污染事实准确性 |

## 8. 非功能需求

| 类别 | 指标 | 适用范围 | 验证方式 |
|------|------|----------|----------|
| 性能 | 景点列表与详情查询 P95 小于等于 2 秒 | FR-01 | 使用 50 并发压测静态查询接口 |
| 性能 | 路线推荐结果返回 P95 小于等于 3 秒 | FR-02 | 使用 30 并发模拟不同路线条件 |
| 性能 | 文本问答首个可见响应小于等于 5 秒，完整结果小于等于 10 秒 | FR-04 | 在稳定网络和标准知识库规模下测量 |
| 性能 | 角色切换反馈时间小于等于 1 秒，完全切换小于等于 3 秒 | FR-05 | 对本地预加载角色进行切换测试 |
| 可用性 | 比赛演示期间服务可用性不低于 99% | 全局 | 通过演示环境监控和故障记录验证 |
| 可恢复性 | 单点模块故障后 15 分钟内可切换到兜底方案 | FR-03、FR-04 | 进行服务降级演练 |
| 安全性 | 管理端必须登录鉴权，操作日志可追溯 | FR-06 | 权限测试与操作审计检查 |
| 安全性 | 用户提问、日志和反馈信息应脱敏存储 | FR-07 | 抽样检查日志样本 |
| 内容可靠性 | 发布内容必须带来源和审核状态 | FR-03、FR-04、FR-06 | 抽样核对后台发布记录 |
| 兼容性 | 首期支持 Chrome、Edge 和主流 Android 浏览器，页面具备响应式布局 | FR-01 至 FR-05 | 跨端兼容测试 |
| 可扩展性 | 新增景点和角色应优先通过配置完成，不要求修改核心业务代码 | FR-05、FR-06 | 新增样例数据进行回归测试 |

## 9. 需求优先级与版本规划

| 阶段 | 目标 | 需求范围 | 交付结果 |
|------|------|----------|----------|
| MVP 阶段 | 跑通核心导览闭环 | FR-01 至 FR-05 | 可演示的游客端主流程 |
| 迭代阶段 | 提升运营和数据闭环 | FR-06 至 FR-08 | 可维护的内容后台和基础日志能力 |
| 增强阶段 | 拉开比赛差异化体验 | FR-09、FR-10 | 场景感知、AR 等增强展示 |

## 10. 需求追踪关系

| 需求编号 | 对应设计重点 | 对应测试重点 |
|----------|--------------|--------------|
| FR-01 | 景点内容模型、前端信息架构 | 列表、详情、空数据兜底 |
| FR-02 | 路线推荐规则、约束输入模型 | 路线结果正确性、异常约束处理 |
| FR-03 | 数字人讲解模块、角色配置装载 | 讲解触发、内容一致性 |
| FR-04 | 问题分类、知识检索、回答生成与兜底 | 命中率、越界问题处理 |
| FR-05 | 角色切换状态管理、上下文保持 | 切换延迟、上下文连续性 |
| FR-06 | 内容后台、发布流、审核记录 | 发布状态流转、权限控制 |
| FR-07 | 日志模型、导出机制 | 脱敏、问题回流统计 |

## 11. 风险、依赖与应对

### 11.1 关键依赖

| 依赖项 | 说明 |
|--------|------|
| 景区基础资料 | 需要至少一套完整景区和景点素材作为首期数据源 |
| 历史文化内容来源 | 需要可靠出处，避免生成式内容失真 |
| 大模型或问答服务 | 问答体验依赖外部模型或本地推理能力 |
| 语音服务 | 若接入语音，需要稳定的 ASR/TTS 服务商或本地方案 |

### 11.2 主要风险与应对

| 风险 | 影响 | 应对方案 |
|------|------|----------|
| 范围过大 | 进度失控，无法按时交付 | 明确 P0/P1/P2，首期只做 1 个景区和 2 到 3 个角色 |
| 问答幻觉 | 回答失真，影响可信度 | 限定知识边界，未命中时明确兜底，不强行回答 |
| 角色表达和事实冲突 | 风格化讲解削弱内容准确性 | 将“知识内容”和“表达风格”分层管理 |
| 内容维护复杂 | 后期更新成本高 | 优先设计配置化内容结构和审核流程 |
| 演示环境不稳定 | 比赛现场效果受影响 | 为讲解、问答和路线功能准备离线兜底数据 |

## 12. 结论

本项目的需求重点不是“做一个会说话的形象”，而是围绕景区导览场景，构建一个可讲解、可问答、可推荐路线、可切换角色、可维护内容的完整闭环。

| 后续工作原则 | 说明 |
|--------------|------|
| 主流程优先 | 先保证 FR-01 至 FR-05 跑通 |
| 内容可信 | 保证文化内容真实可控 |
| 风格与事实分层 | 角色表达有差异，但不牺牲事实准确性 |
| 文档闭环 | 需求、设计和测试必须相互对应 |
